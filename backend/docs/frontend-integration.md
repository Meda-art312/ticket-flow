# Frontend integration: ticketflow-api-v1

Backend sources, images and tests are independent of frontend code. Contract source of truth: `docs/openapi.json`; generated by `node scripts/contract.mjs` in the development container. `npm run contract:export` copies the checked-in artifact. Local/test API also serves `GET /api/v1/openapi.json`. Do not change snake_case, enums or nullable fields to match later UI assumptions.

## Addresses and proxy

API: http://localhost:3000/api/v1. API documentation: http://localhost:3000/docs. Mailpit: http://localhost:8025. Default frontend origin: http://localhost:8080. A separately started frontend joins `ticketflow-local` (or `TICKETFLOW_NETWORK`) and proxies `/api/v1` to `http://api:3000`. Docker DNS addresses are never browser return URLs. Backend tests run without that proxy.

Configure exactly one `FRONTEND_ORIGIN` with no path or trailing slash. CORS credentials are allowed only for that origin. The initial deployment does not trust forwarded headers. Configure explicit TLS termination and `COOKIE_SECURE=true`; do not turn on blanket trust proxy. A browser on localhost:8080 can call localhost:3000 directly with credentials for local integration.

## Authentication

Register: POST /auth/register with `{email,password,display_name}`; creates customer only, privileged fields are rejected. Password length 12–128. Login: POST /auth/login with `{email,password}`. Response: `{access_token,expires_in:900}`. Keep access tokens in browser memory; send `Authorization: Bearer ...`. `/me` returns current database role memberships.

Refresh and logout: POST /auth/refresh or /auth/logout with `{}`, `credentials: 'include'`, and the refresh cookie. Login/registration/refresh/logout POSTs require `Origin` exactly equal to FRONTEND_ORIGIN; missing, null and cross-site fetch metadata are rejected. Refresh tokens are not returned in JSON. Cookie: `refresh_token`, HttpOnly, SameSite=Lax, Path=/api/v1/auth, Secure under configured HTTPS; local/test HTTP can explicitly disable Secure. Logout clears matching attributes. Rotation reuses no token: concurrent refresh calls produce one success and one reuse rejection, revoking the entire family including the replacement. Serialize refresh calls in the client and sign in again after a reuse rejection. Previously issued access tokens can survive logout for up to 15 minutes; privileged roles are always checked against SQL.

CLI example (PowerShell use curl.exe):

```sh
curl -c cookies.txt -H 'Origin: http://localhost:8080' -H 'Content-Type: application/json' -d '{"email":"customer@ticketflow.local","password":"Local-demo-password-2026!"}' http://localhost:3000/api/v1/auth/login
curl -b cookies.txt -c cookies.txt -H 'Origin: http://localhost:8080' -H 'Content-Type: application/json' -d '{}' http://localhost:3000/api/v1/auth/refresh
```

## Reservation and payment

POST /bookings `{category_id,quantity}` with a fresh `Idempotency-Key`. Quantity 1–6; price is calculated on the server. Same key and payload returns one logical result; changed input gives 409. The same rule applies to checkout, cancel, refund and demo completion. Keys are actor/operation scoped, 1–128 characters `[A-Za-z0-9_.:-]`, retained at least seven days.

`expires_at` is authoritative on the server; render countdowns relative to `server_time`. The normal hold is 600 seconds. Local/test can set RESERVATION_SECONDS to a smaller value. A delayed worker never extends eligibility.

POST /bookings/:id/checkout `{}` returns `{attempt_id,status,checkout_url,mode}`. `pending` means the existing financial attempt is being recovered. Poll booking/checkout with the original key; do not initiate another charge identity. Simulator URL: `${FRONTEND_ORIGIN}/demo/checkout/:sessionId`. GET /demo/checkout/:sessionId requires normal owner authentication. POST its /complete action with `{outcome:'success'|'decline'}` and Idempotency-Key atomically accepts one outcome, then signed server-generated evidence enters the durable webhook inbox. Completion is asynchronous: poll the booking for CONFIRMED/tickets. No simulator signing/control secrets are returned. All demo routes are disabled in production.

Stripe test return: `${FRONTEND_ORIGIN}/checkout/return?booking_id=:id`. This URL proves nothing; poll the API. Payment, refund and artifact state are separate from booking state. A late success leaves the reservation EXPIRED/CANCELED and creates compensation. Respect `allowed_actions` and their reasons instead of inferring eligibility in UI code.

Ticket endpoints are owner-only. `check_in_token` is opaque; submit it in a check-in JSON body, never a URL. `qr_svg` is server-generated SVG or null while PENDING/FAILED. Display as an image/blob; do not inject arbitrary HTML. Confirmation remains valid when email or QR rendering fails.

## Local fixtures

Seed password is SEED_PASSWORD from explicit local configuration; default example is `Local-demo-password-2026!`. Accounts: customer@ticketflow.local, organizer@ticketflow.local, organizer2@ticketflow.local, admin@ticketflow.local. Two organizers prove ownership isolation. No public privilege registration.

| Scenario | Event UUID | Category UUID |
|---|---|---|
| Refund eligible (starts +72h) | 20000000-0000-4000-8000-000000000001 | 30000000-0000-4000-8000-000000000001 |
| Check-in eligible (starts +1h) | 20000000-0000-4000-8000-000000000002 | 30000000-0000-4000-8000-000000000002 |
| Contention (capacity 10) | 20000000-0000-4000-8000-000000000003 | 30000000-0000-4000-8000-000000000003 |

Seed is idempotent and does not reset commercial terms or inventory. Time windows are relative to first seed; create fresh fixtures if old events have elapsed. Money: USD 2500 minor units per seeded ticket. Use separate bookings/events for refund and admission demonstrations.

Commands can replay their original logical snapshot; fetch booking detail afterward for current state/server_time. Stripe card declines can leave the same hosted session PENDING: reuse that attempt's URL. A definitively failed refund exposes REFUND_REQUIRES_REVIEW for operator investigation. APP_MODE must be explicit (Compose supplies it). Set COOKIE_SECURE=true for HTTPS; incompatible URL/cookie settings are rejected.

Swagger runs on the API origin, but auth POSTs still require the configured Origin. Use the CLI/cookie-jar examples by default. For local interactive Swagger authentication, deliberately configure FRONTEND_ORIGIN=http://localhost:3000 and recreate API/worker. The independent frontend normally uses localhost:8080.

## Errors and pagination

Errors have `{code,message,request_id,field_errors?}`. Stable codes include INVENTORY_UNAVAILABLE, EVENT_NOT_ON_SALE, HOLD_INELIGIBLE, IDEMPOTENCY_CONFLICT, REFUND_INELIGIBLE, TICKET_UNUSABLE, UNTRUSTED_ORIGIN and REFRESH_REUSE_OR_EXPIRED. HTTP 404 hides inaccessible individual resources. Lists use `{items,pagination:{page,page_size,total}}`, default 1/20, maximum 100. Organizer management collections currently return bounded `items` collections; see contract for their exact schemas.
